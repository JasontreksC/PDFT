# PDFT — PDF 번역기 (Docker)

PDF의 **글자와 그 글자가 인쇄된 위치를 그대로 읽어 → LLM으로 번역 → 원본 쪽 위에 번역문을 얹는** 웹앱입니다.
원본 쪽을 버리고 다시 조판하지 않습니다. 선·표 테두리·음영·로고·그림·벡터 도표는 원본 그대로 남고, **글자만** 지우고 번역문을 같은 자리에 넣습니다.
번역문이 길거나 짧으면 주변의 빈 공간만큼 늘리고, 줄이고, 아래 글을 당기거나 밀어 맞춥니다. 번역 요청에는 **텍스트만** 전송됩니다.

## 실행

```bash
cp .env.example .env            # 사용할 번역 LLM 키 입력
docker compose up --build
# → http://localhost:8000
```

`.env` 예: `OPENAI_API_KEY=...` (번역 LLM 키만 필요합니다).
처음 실행하면 `config/models.json`이 예제로 자동 생성됩니다. 컨테이너에는 Noto Sans/Serif KR·JP·SC(가변), Nanum, Liberation, DejaVu 폰트가 들어 있습니다.

| 볼륨 | 용도 |
|---|---|
| `./config` | `models.json` (번역 LLM 엔트리포인트·키·모델명) |
| `./data` | 업로드한 PDF, 분석 결과, 번역, 내부 컨텍스트 |
| `./fonts` | 추가 폰트(.ttf/.otf)를 넣고 컨테이너 재시작 |

> 포트는 `127.0.0.1`에만 바인딩됩니다. 로그인 기능이 없고 내 API 키를 쓰므로 외부에 그대로 노출하지 마세요.

## 사용법

1. **파일 → PDF 열기** (또는 끌어다 놓기). 이 시점에는 아무 비용도 들지 않습니다.
2. **문서 분석**을 누릅니다. **텍스트 층이 있는 PDF는 PDF 글자와 좌표만으로** 분석됩니다. **Docling 힌트** 칸(기본 켜짐)을 켜 두면 로컬 Docling이 읽은 구역을 "이 줄들이 한 글인가" 판단의 힌트로 추가로 씁니다.
   텍스트 층이 없는 **스캔 쪽이 있으면** 글자를 읽기 위해 로컬 Docling이 반드시 필요합니다 (아래 "로컬 Docling"). 서비스가 꺼져 있으면 스캔 문서는 분석할 수 없고, 텍스트 문서는 힌트 없이 분석합니다.
3. 분석이 끝나면 원본 쪽이 그대로 보입니다. **모델**과 **번역 언어**를 고르고 **번역 시작**. 끝난 글부터 화면에 반영되고, 중지 후 **이어서 번역**할 수 있습니다.
4. 글을 **클릭**하면 바로 위에 컨트롤 패널이 뜹니다: **글꼴 · 굵기 · 크기 · 색** (이 네 가지만). 바꾸면 그 쪽만 다시 조판됩니다.
5. **글꼴** 메뉴에서 기본 글꼴, **PDF 저장**으로 내보내기.
6. **파일 → 최근 작업**에서 작업마다 **✕**로 삭제하거나(PDF·분석 결과·번역이 모두 지워지며 되돌릴 수 없음), **다른 작업 N개 모두 삭제**로 지금 열려 있는 작업만 남기고 지울 수 있습니다. 분석 중인 작업은 삭제할 수 없습니다.

**쪽 선택 (왼쪽 목록)** — 문서를 열면 왼쪽에 쪽 썸네일 목록이 나옵니다 (툴바의 **▤ 쪽**으로 숨기기/보이기).
* 썸네일 왼쪽 위 체크박스로 쪽을 고르고, **Shift+클릭**으로 범위, **Ctrl/⌘+클릭**으로 개별 토글, **전체 선택 / 전체 해제** 버튼을 씁니다. 썸네일을 클릭하면 그 쪽으로 이동합니다.
* **선택한 쪽만 작업합니다**: 번역 시작/이어서 번역은 선택한 쪽의 글만 번역하고, **번역 초기화**는 선택한 쪽의 번역만 지우며(전체 선택일 때만 내부 컨텍스트도 초기화), **파일 → 선택한 쪽만 PDF 저장**은 선택한 쪽만 새 PDF로 저장합니다. 선택하지 않은 쪽은 원본 그대로 남습니다.
* **↩ 번역 전으로**: 선택한 쪽의 번역과 서식(글꼴·굵기·크기·색) 변경을 지우고 원본 상태로 되돌립니다. 다른 쪽은 그대로이고, 전체 선택일 때만 내부 컨텍스트도 초기화합니다. (번역 메뉴의 "번역 초기화"는 번역만 지우고 서식은 유지합니다.)
* 썸네일의 ✓는 번역된 쪽, …는 일부만 번역된 쪽입니다. 선택은 작업별로 저장되고, 번역 중에는 바꿀 수 없습니다. 선택이 없으면 번역 버튼이 비활성화됩니다.
* 여러 쪽에 반복되는 머리글·바닥글은 선택한 쪽 안에서만 적용됩니다 (이미 번역된 같은 문구가 있으면 다시 번역하지 않고 재사용).

## 문서를 읽는 방식

```
PDF ──► 텍스트 층 (글자 + 굵게/링크 + 정확한 좌표)
    ──► 글상자(frame) 구성            "이 줄이 앞 줄의 줄바꿈 연속인가"만 판정. 문단/표/목록 같은 분류는 하지 않음
    ──► 번역 (글상자 단위)            컨텍스트·용어사전 누적
    ──► 원본 쪽에 얹기 (MuPDF)        글자만 삭제(그래픽 유지) → 같은 자리에 번역문, 필요하면 흐름 배치
```

**글상자(frame)** = 원본 쪽에 한 덩어리로 인쇄된 글 (줄바꿈으로 이어지는 문단, 제목, 목차의 제목 한 줄, 표 셀 하나, 쪽번호 …).
두 줄이 한 글상자가 되는 조건은 조판의 규칙 그 자체뿐입니다:

* 아래 줄이 바로 밑에 있고, 크기가 비슷하고, 왼쪽/오른쪽/가운데 선을 공유한다 (첫 줄 들여쓰기·글머리표 내어쓰기 허용)
* **줄바꿈 규칙**: 줄이 바뀌는 이유는 다음 낱말이 안 들어가서이므로, 윗줄이 글상자의 오른쪽 끝까지 차 있어야 한다
* 줄 간격이 **그 문서가 실제로 쓰는 줄 간격** 중 하나와 같다 (3줄 이상 문단의 확실한 줄바꿈에서 글자 크기별로 측정하며, 같은 크기라도 본문 1.36배·표 안 1.23배처럼 여러 개가 있을 수 있음)
* 글머리표·"1."·콜론으로 끝나는 라벨·굵게↔보통 변화·(힌트가 있으면) 다른 파서 구역은 새 글상자

한 줄 안에서 멀리 떨어진 조각(목차의 제목과 쪽번호)은 처음부터 별개의 글상자입니다. 판정이 틀려도 글이 인쇄된 자리는 그대로여서 **줄바꿈이 조금 어색해질 뿐 구조는 깨지지 않습니다.**

* **원본 쪽 유지**: 번역한 글의 글자만 지우고(이미지·선 그래픽은 유지) 그 자리에 번역문을 넣습니다. 링크 밑줄 선도 같이 지웁니다. 번역하지 않는 글(URL, 숫자, 그림 안의 글자, 코드)은 그대로 남습니다.
* **자리 배치**: ① 원래 상자 ② 옆 빈 공간으로 넓히기(한 줄 글) / 아래 빈 공간으로 늘리기 ③ 그래도 안 되면 글자 크기를 55%까지 줄이기.
  빈 공간은 기하로만 판단합니다 — 다른 글, 선, 상자, 그림이 인쇄된 곳은 막히고, 표 셀·음영 상자·그림 안의 글은 그 안에서만 움직입니다.
* **흐름 배치**: 옆에 다른 글이 없고 상자 안이 아닌 글은 위에서 아래로 쌓아, 번역문이 짧아져 생긴 빈틈은 아래 글을 당겨 메우고 길어지면 밀어 냅니다(원본의 글 사이 간격 유지). 선·그림·번역하지 않는 글에 닿으면 거기서 멈춥니다.
* **머리글·바닥글**: 여러 쪽에서 같은 자리에 반복되는 글은 한 번만 번역해 모든 쪽에 적용합니다. 로고와 구분선은 원본 쪽 그대로입니다. 쪽번호는 원본 번호 그대로 남습니다.
* **표지·전면 이미지 쪽**은 원본 쪽을 그대로 가져옵니다 (쪽 전체가 그림 한 장이고 글자가 30단어 미만인 쪽, 글자 있는 문서에 한함).
* **스캔 쪽**(텍스트 층 없음)은 로컬 Docling이 읽은 글과 위치를 쓰고, 번역문이 들어갈 자리는 주변 색으로 칠해 원본 글을 가립니다. 글자 크기는 영역 크기로 추정하므로 정밀도가 낮고, 표·그림 속 글자는 번역하지 않습니다. OCR 텍스트 층이 있는 스캔 PDF는 그 층의 좌표를 그대로 씁니다.
* **서식 보존**: 굵게(`**`)와 링크(`[글](url)`)는 번역 후에도 유지하도록 LLM에 지시합니다. 글자 크기·색·굵기는 글상자별로 PDF에서 읽어 옵니다.

## 로컬 Docling (맥 Apple GPU)

스캔 쪽 읽기(OCR)와 구역 힌트는 **로컬 Docling**이 맡습니다. 무료이고 문서가 외부로 나가지 않습니다.

**Docker 컨테이너 안에서는 맥 GPU(MPS)를 쓸 수 없습니다** (Docker Desktop은 리눅스 VM이라 Metal이 없음). 그래서 Docling은 **맥에서 직접** 도는 작은 서비스(`docling_host/`)로 두고 컨테이너가 `host.docker.internal:8765`로 부릅니다.

```bash
./docling_host/run.sh        # 처음에는 .venv를 만들고 Docling을 설치합니다 (모델은 처음 사용할 때 내려받음)
docker compose up -d --build # docker-compose.yml이 docling_host 폴더를 읽기 전용으로 마운트해 토큰을 읽습니다
```

* 서비스는 `0.0.0.0:8765`에서 듣고(컨테이너가 접속해야 하므로) **토큰**(`docling_host/.token`, 첫 실행 때 자동 생성)이 없으면 거절합니다. 같은 와이파이의 다른 기기에서 접근되지 않게 하려면 방화벽에서 8765를 막거나 신뢰하는 네트워크에서만 쓰세요. 앱을 맥에서 직접 실행하면 `HOST=127.0.0.1 ./docling_host/run.sh`로 이 컴퓨터에서만 열 수 있습니다.
* **측정 (M5 MacBook Air, 6쪽 발췌본, 모델 적재 후)**: 레이아웃 분석 CPU 0.36초/쪽 → **MPS 0.13초/쪽 (약 2.8배)**. 288쪽 책은 약 40초 대 105초입니다. 스캔 쪽 OCR은 macOS 내장 Vision(`ocrmac`)이 자동으로 쓰여 쪽당 약 0.6초입니다 (첫 실행은 모델 적재로 수십 초).
* **표 구조 인식은 끄고 씁니다** (번역에는 필요 없고 MPS에서도 0.61초/쪽으로 느림). 끄면 Docling은 표 안 글을 줄 단위 항목으로 줍니다. 텍스트 쪽에서는 이 항목을 구역 힌트로 쓰지 않고(줄마다 끊기는 것을 막기 위해), 스캔 쪽에서는 이 줄들을 PDF 글자를 읽을 때와 같은 규칙으로 문단으로 다시 묶습니다 (OCR 상자가 들쭉날쭉해서 텍스트 층보다는 덜 정확하게 묶임).
* 서비스가 꺼져 있으면 분석 상자 옆에 "서비스 꺼짐"이 빨갛게 표시됩니다. 환경 변수: `PDFT_DOCLING_URL`, `PDFT_DOCLING_TOKEN`(또는 `PDFT_DOCLING_TOKEN_FILE`).
* 이전 버전에서 클라우드 파서로 분석한 작업의 `parse.json`은 형식이 같아 "구조 다시 정리"에서 그대로 읽히지만, 새로 분석하면 Docling 결과로 바뀝니다.

## 번역 LLM 설정: models.json

```json
{
  "models": [
    {
      "id": "openai-gpt-4.1-mini",          // 고유 id
      "name": "OpenAI · GPT-4.1 mini",      // 메뉴에 표시될 이름
      "type": "openai",                     // openai | anthropic | gemini
      "endpoint": "https://api.openai.com/v1",
      "api_key": "${OPENAI_API_KEY}",       // 직접 입력하거나 ${환경변수}
      "model": "gpt-4.1-mini",
      "context_window": null,               // (선택) 컨텍스트 한도를 직접 지정
      "max_output_tokens": 8192,            // (선택) anthropic/gemini 출력 상한
      "params": { "temperature": 0.2 },     // (선택) 요청 본문/generationConfig에 그대로 병합
      "prompt_cache_key": null,             // (선택) true면 작업별 prompt_cache_key 전송 (api.meta.ai / api.openai.com은 자동)
      "headers": {}                         // (선택) 추가 헤더
    }
  ]
}
```

* `type: "openai"`는 `/chat/completions` 호환 서버 전부(OpenAI, Meta AI, OpenRouter, Together, Groq, DeepSeek, vLLM, LM Studio, Ollama 등)에 쓸 수 있습니다. 실제 JSON에는 주석을 쓸 수 없습니다(위 `//`는 설명용).
  수정 후 **모델 → models.json 다시 읽기**로 재시작 없이 반영됩니다. API 키는 서버 밖으로 나가지 않습니다.
* **컨텍스트 한도 조회** 순서: `models.json`의 `context_window` → 제공자 API(Anthropic `max_input_tokens`, Gemini `inputTokenLimit`, OpenAI 호환 `/models`의 `context_length`, Ollama `/api/show`) → 모델명 내장 표(추정) → 8,192.
  Meta AI처럼 한도를 알려주지 않는 곳은 `context_window`를 직접 지정하세요.
* **컨텍스트 누적/압축 + 용어사전**: 번역한 원문·번역문 쌍이 컨텍스트에 쌓이고, 압축 시작 지점(기본 한도의 70%)을 넘으면 LLM이 요약으로 압축합니다.
  **비용 보호 상한**: 요청마다 이 컨텍스트가 통째로 다시 전송되므로, 모델 한도와 무관하게 압축 시작 지점은 `PDFT_CONTEXT_CAP`(기본 24,000 토큰)을 넘지 않습니다.
  (한도 100만 토큰 모델에서 상한 없이 70%로 두면 이력이 70만 토큰까지 쌓여 요청마다 재전송됩니다 — 288쪽 책에서 입력이 문서의 수백 배가 되었습니다.)
  재시도 요청에는 이력을 싣지 않습니다.
  **프롬프트 캐시**: 요청 앞부분(시스템 프롬프트·요약·이력)을 항상 같은 순서로 두고, 요청마다 달라지는 용어사전과 이번 문단은 맨 뒤에 둡니다.
  api.meta.ai와 api.openai.com에는 `prompt_cache_key`(작업별 고정값)를 자동으로 보냅니다. 다른 OpenAI 호환 서버는 `models.json`에 `"prompt_cache_key": true`로 켤 수 있습니다.
  Meta API 실측: 키 없이/용어사전을 이력 앞에 두면 캐시 적중 0%, 키를 보내고 이력을 앞에 두면 98%(`usage.prompt_tokens_details.cached_tokens`). 상태바의 "캐시 n%"로 확인할 수 있습니다. 작업별 **누적 LLM 입력/출력 토큰과 요청 수가 하단 상태바에 표시**됩니다. 새 전문 용어는 문서 단위로 누적됩니다.
  이 내용은 `data/jobs/<id>/internal/`에만 저장되며 어떤 API 응답에도 없고, UI에는 토큰 수치(게이지)만 나옵니다.
* **동시 요청 (모델 메뉴 → 속도)**: 동시에 번역할 쪽 수(1~16, 기본 4)입니다. 각 쪽은 시작할 때의 컨텍스트(요약·이전 번역 쌍·용어사전) 사본으로 번역하고 끝나면 새 번역 쌍·용어를 공유 컨텍스트에 합칩니다. 한 쪽 안의 요청 묶음도 동시에 보내며, 전체 동시 요청 수는 이 값을 넘지 않습니다.
  컨텍스트 압축은 진행 중인 요청이 없을 때만 합니다(요약이 요청 도중 바뀌지 않도록). 429(요청 한도)는 `Retry-After`를 따라 자동 재시도하지만 API가 동시 요청을 제한하면 값을 낮추세요.
  **같은 시점에 번역되는 쪽끼리는 서로의 번역과 새 용어를 보지 못하므로** 용어 일관성이 조금 떨어질 수 있습니다 (1 = 순차, 용어 일관성 최대). 토큰 사용량은 비슷하고, 프롬프트 캐시 적중이 약간 줄 수 있습니다.
* LLM 호출 함수는 문자열 두 개(`system`, `user`)만 받습니다. 페이지 이미지가 전송될 경로가 없습니다.

## 한계

* **개인정보**: 분석은 모두 내 컴퓨터 안에서 이뤄집니다 (PDF 글자 읽기 + 로컬 Docling). 번역 LLM에는 텍스트만 갑니다.
* **기울임**은 반영되지 않습니다 (가변 폰트에 이탤릭 면이 없음 → 일반체). 굵게·링크 색/밑줄은 반영됩니다. 링크는 **클릭 가능한 주석으로는 새로 만들지 않습니다** (원본의 링크 영역은 그대로 남지만 글이 움직이면 어긋날 수 있음).
* 그림 안의 글(스크린샷, 도표 속 글자)은 번역하지 않습니다. 벡터 도표 속 글자도 그림 위에 인쇄된 것이면 원본 그대로입니다.
* 번역문이 매우 길어 아래가 선·그림으로 막힌 곳은 글자가 작아집니다 (최소 55%, 그래도 안 들어가면 더 줄여서 글이 사라지지 않게 합니다). 글은 그려진 높이를 기준으로 아래 글을 밀기 때문에, 선·URL 같은 고정 요소와 겹치지 않도록 자리를 계산합니다. 그래도 안 들어가면 넘치는 개수가 상태바에 표시됩니다. 번역문 때문에 다음 쪽으로 이어 붙이지는 않습니다 (쪽 구성은 원본과 같음).
* **옆에 다른 글이 있는 글**(2단 조판, 표 셀, 그림 설명 옆 글)은 흐름 배치를 하지 않고 제자리에서 맞춥니다. 번역하지 않는 글(URL 등)이 글 사이에 끼어 있으면 거기서 흐름이 끊겨 빈틈이 남을 수 있습니다.
* 머리글·바닥글 자리에서 쪽마다 내용이 달라지는 글(장 제목 등)은 쪽별로 따로 번역됩니다. 회전된 글자(세로쓰기·회전 쪽)는 건드리지 않습니다.
* 스캔 쪽의 한계는 위 "스캔 쪽" 항목을 보세요 (파서가 제목을 머리글에 합쳐 버리면 그 제목은 번역되지 않습니다).
* **다시 분석**하면 번역과 내부 컨텍스트가 초기화됩니다. **번역 메뉴 → 구조 다시 정리 (비용 없음)**은 같은 방식으로 글상자를 다시 만들고 원문이 같은 글의 번역은 옮겨 줍니다 (앱 업데이트 후 이전 작업에 적용할 때). 이전 버전(쪽 흐름 방식)에서 만든 작업은 처음 열 때 "다시 분석" 상태로 바뀌며 번역은 옮겨지지 않습니다 (`doc.v1.json`으로 보관).
* 서버는 워커 1개입니다 (번역 작업이 프로세스 내 태스크). 인증이 없으므로 개인용입니다.

## 검증 내역

AWS 치트시트 책(288쪽)의 표본 쪽(표지, 목차, 본문, 글머리표, 테두리·음영 표, 스크린샷, 코드 상자)과 단일 쪽 PDF 2개를 실제 모델로 번역해 배치와 보존을 확인했습니다
(API: 업로드 → 분석 → 번역 → 글 클릭·크기 변경 → 내보내기). 이미지만 있는 쪽은 Cost-effective로 확인했습니다. 번역 문구의 정확성은 사용하는 LLM에 달려 있고 이 검증에는 포함되지 않습니다.
2단 조판·세로쓰기·회전 쪽은 시험하지 못했습니다.

## 개발

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r backend/requirements.txt
PDFT_DATA_DIR=./data PDFT_CONFIG_DIR=./config PDFT_FONT_DIRS=./fonts:/path/to/fonts \
PDFT_FRONTEND_DIR=./frontend PDFT_EXAMPLE_MODELS=./config/models.example.json \
  uvicorn app.main:app --app-dir backend --reload --port 8000
```

주요 API: `GET /api/bootstrap`, `POST /api/jobs`(업로드), `POST /api/jobs/{id}/analyze {hints}`, `GET /api/docling`(로컬 서비스 상태), `POST /api/jobs/{id}/translate {model_id, target_lang, concurrency, ...}`, `POST /api/jobs/{id}/cancel|compress`, `POST /api/jobs/{id}/reset {restore_styles}`, `PUT /api/jobs/{id}/selection {pages}`(작업 대상 쪽),
`GET /api/jobs/{id}/status`, `GET /api/jobs/{id}/pages/{n}/image|boxes`, `PATCH /api/jobs/{id}/blocks/{frame}`(글꼴/굵기/크기/색), `GET /api/jobs/{id}/export[?selected=true]`.

구조: `docling_host/`(맥에서 도는 로컬 Docling 서비스) · `parse/`(Docling 서비스 클라이언트, Docling→파서 결과 변환) · `structure/`(텍스트 층 읽기·읽기 순서) · `frames/`(글상자 구성 `build.py`, 원본 쪽 위 조판 `compose.py`, 쪽 기하 `geometry.py`) · `compose/`(마크업→HTML, 재조판 매니저) · `translate/`(프롬프트·컨텍스트·파이프라인) · `llm/` · `pdf/`(폰트·렌더).
